# 05 — SearchAgent's Fusion Method

## Question

[Experiment 04](04-indexing-strategy.md) proved the naive `bool(knn, match)` combination silently degrades to BM25-only (unbounded BM25 scores drown the bounded cosine-similarity scores in the sum), and rejected it — but left the actual replacement as a follow-up: "use a score-normalization search pipeline or weighted RRF, tuned once SearchAgent exists." Now that SearchAgent is being built, which of those actually works better, and at what weighting?

## Terminology

- **Weighted RRF**: Reciprocal Rank Fusion (defined in [Experiment 04](04-indexing-strategy.md)), extended so each ranked list's contribution is scaled by a weight before summing: `weight / (C + rank)`. Unweighted RRF (weight 1.0 for every list) treats every method as equally trustworthy regardless of how well it actually performs alone — weighting lets a stronger method (here, BM25, per Experiment 04's results) count for more.
- **Score normalization + weighted combination (OpenSearch's native `hybrid` query)**: a real, built-in OpenSearch mechanism (the `opensearch-neural-search` plugin, confirmed installed on this domain via `_cat/plugins` rather than assumed) that rescales each sub-query's scores onto a comparable [0, 1] range per query (`min_max` normalization) *before* combining them with a weighted average (`arithmetic_mean`) — the fix for exactly the scale-mismatch problem Experiment 04 found, applied properly instead of a raw sum.
- **precision@k / hit rate@k**: same definitions as Experiments 03 and 04.

## Method

Same corpus, synthetic queries, and ground truth as Experiment 04 (300 real long reviews, 30 synthesized queries, sentence-aware chunking). Compared against the same index:

- **`rrf_unweighted`** — carried over from Experiment 04 as a reference point
- **`rrf_favor_bm25_2to1`**, **`rrf_favor_bm25_3to1`** — weighted RRF, BM25 weighted 2x and 3x over kNN (BM25 individually outperformed kNN in Experiment 04 — 0.213 vs 0.207 precision@5 — so weighting toward it is the natural first thing to try, not an arbitrary sweep)
- **`native_hybrid_equal`** (0.5/0.5) and **`native_hybrid_favor_bm25`** (0.7/0.3) — OpenSearch's native `hybrid` query with a `normalization-processor` search pipeline (`min_max` + `arithmetic_mean`)

Script: [`scripts/experiments/run_searchagent_fusion_experiment.py`](../../scripts/experiments/run_searchagent_fusion_experiment.py), built on the same [`retrieval_eval_utils.py`](../../scripts/experiments/retrieval_eval_utils.py) as Experiments 03-04.

## Results

| Method | precision@5 | hit_rate@5 |
| --- | --- | --- |
| bm25_only (reference, from Exp. 04) | 0.213 | 0.967 |
| knn_only (reference, from Exp. 04) | 0.207 | 0.933 |
| rrf_unweighted | 0.193 | 0.967 |
| rrf_favor_bm25_2to1 | 0.180 | 0.900 |
| rrf_favor_bm25_3to1 | 0.180 | 0.900 |
| **native_hybrid_equal** | **0.200** | **0.967** |
| native_hybrid_favor_bm25 | 0.200 | 0.967 |

**None of the tested fusion methods beat plain BM25.** Weighting RRF toward BM25 made it *worse*, not better (0.180 vs unweighted's 0.193) — RRF is rank-based, not magnitude-based, so pushing weight toward the method that's already winning distorts the fused ranking in a way that doesn't track actual relevance past the top result. Native hybrid (either weighting) ties BM25 on hit rate and trails slightly on precision, but is close enough (0.200 vs 0.213, n=30) not to be a clear loss.

## Why this doesn't mean "drop the kNN clause"

This result looks like it argues for BM25-only, but the eval methodology has a specific, relevant blind spot: **synthetic queries are generated by asking Claude to paraphrase the *same review* they're graded against** (see Experiment 03's methodology). That paraphrase tends to retain some of the source review's vocabulary, which structurally favors BM25 — a keyword-matching method — regardless of how good vector search actually is. The design's own motivating case for semantic search (design doc [02](../designs/02-retrieval-agents.md): *"'good bass' needs semantic search — bass quality isn't a field"*) is precisely a query with **low** lexical overlap with the source text, which this query set doesn't exercise. A synthetic eval that generates queries *from* the target document structurally can't measure the scenario hybrid search exists for.

## Decision

**SearchAgent uses OpenSearch's native `hybrid` query with a `min_max` normalization pipeline, equal weighting (0.5/0.5).** Not because it won this eval — it didn't, clearly — but because:
- It's the real, documented fix for the scale-mismatch bug Experiment 04 found (unlike weighted RRF, which made things worse here)
- Its shortfall against BM25 in this eval is small (0.013 precision@5 on n=30 — not a confident gap) and plausibly an artifact of the query-generation blind spot above, not a genuine hybrid-search weakness
- Dropping the kNN clause entirely would remove the exact capability (matching on meaning, not just words) that FR1/FR5 and the design's own motivating example require

Equal weighting over favor-BM25 because the two tied exactly in this eval (0.200/0.967 both) — no basis here to justify favoring one input over the other.

**Known limitation, and a concrete follow-up**: this decision should be re-checked against queries that do NOT share vocabulary with their target chunk — e.g., queries built from a *paraphrase of a paraphrase*, or, better, real usage logs once SearchAgent is live. Until then, treat the fusion-method choice as "best available real mechanism, not yet proven to beat the naive alternative on this specific query style" rather than a fully closed question.
